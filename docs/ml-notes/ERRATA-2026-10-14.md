## 3. Clustering: what the evidence supports

The notes conclude that "the data supports k=2". The defensible headline is
weaker: **no distinct day-types were found.** The notes' own cross-method
agreement (ARI 0.35 to 0.60) and flat silhouette curve (0.13 to 0.21) already
point that way. Two additions explain why "k=2" should not be read as structure:

- **No no-structure baseline was run.** A silhouette of 0.205 means nothing until
  you know what silhouette k-means gets on data with *no* clusters.
- **A stable two-way split is expected for almost any data.** Cut a single
  continuous cloud along its main axis of variance and k-means will split it into
  a "high" half and a "low" half, and that split is reproducible under
  resampling, because the axis itself is real. Stability tells you the
  *partition* is repeatable; it does not tell you the data are *clustered*. The
  notes' own finding that the two clusters are "overall glucose control that day"
  (restating TIR) is exactly this: one gradient, cut in half.

**A test you could run (good practice for this kind of work).** Compare your
real silhouette with the distribution you get from reference data that has the
same marginals but no cluster structure:

1. *Gaussian reference:* fit a multivariate normal to the scaled features (same
   mean and covariance), draw 548-row samples, apply the same coverage filter
   size, run the same k sweep, and record silhouette per k. Repeat 200 times.
2. *Column-shuffle reference:* independently permute each feature column. This
   keeps every feature's distribution but destroys the joint structure.
3. Plot the real silhouette per k against the 95th percentile of the reference
   curves. If the real value is not clearly above it, there is no evidence of
   cluster structure at that k. Expect k=2 to be the hardest to beat honestly,
   for the reason above.
4. The **gap statistic** (Tibshirani et al., 2001) is the formal version:
   compare log within-cluster dispersion on the real data with its expectation
   under a uniform reference, pick the smallest k whose gap is within one
   standard error of the next. `sklearn` has no built-in; it is about 20 lines
   on top of `KMeans`. Note that a PCA-rotated uniform reference is
   the usual recommended variant.

Be careful with the Gaussian reference: real day features are skewed and bounded
(fractions in [0, 1]), so also try the shuffle reference, which respects that.

## 4. Supervised: accuracy is the wrong lens here

The notes compare accuracy: forest 0.762 vs majority class 0.789. Accuracy is
the fraction of all rows right, so on a 79% class a model that predicts the
majority label every time scores 0.789 for free. A class-balanced forest
(`class_weight="balanced"`) deliberately trades some majority-class accuracy for
minority-class recall, so judging it by accuracy penalizes it *by design*. That
is the wrong yardstick for the question being asked ("is there any signal for the
rare outcomes?").

Recomputed from the notes' per-class table (test fold, n=323):

Random forest, macro-F1 = mean of per-class F1:
`(0.20 + 0.00 + 0.86) / 3 = 1.06 / 3 = 0.353`

Majority classifier (always predicts `uncovered`):
- uncovered: recall = 1.00; precision = 255 / 323 = 0.789;
  F1 = 2 * 0.789 * 1.00 / (0.789 + 1.00) = 0.882
- late_bolused and pre_bolused: never predicted, so F1 = 0.00 each
- macro-F1 = `(0.882 + 0 + 0) / 3 = 0.294`

Balanced accuracy (mean per-class recall) tells the same story:
forest `(0.15 + 0.00 + 0.93) / 3 = 0.360`, majority `(0 + 0 + 1) / 3 = 0.333`.

Why these are the better lens: macro-F1 and balanced accuracy weight each class
equally regardless of size, so they reward a model for finding the 6% and 23%
classes instead of ignoring them. Seen that way the forest is slightly ahead
(0.35 vs 0.29 macro-F1), not behind. **"Weak signal" still stands**: 0.35 is
barely above the 0.29 floor, `pre_bolused` is still 0/15, balanced accuracy is
only 0.027 above chance for three classes, and with 15 and 53 test positives
those gaps are well inside what resampling noise could produce. Worth adding:
a bootstrap confidence interval on the macro-F1 difference, and the
`HourOfDayBaseline` scored on the same metric (it was not here). The honest
summary is "weak, possibly-nonzero signal that this evaluation is too small to
confirm", not "worse than the baseline".

## 5. LLM assistant: deployment-readiness (not bugs)

All four checked against `apps/personal/telegram/llm_assistant.py`,
`handler.py` and the requirements files. None block the feature's current
inert, off-by-default state.

- **Model IDs.** `_DEFAULT_MODEL = "claude-opus-5"` (about L132) is the previous
  generation. Current IDs are `claude-opus-5-5`, `claude-sonnet-5-5` and
  `claude-haiku-5-5`. The note's suggestion to trial `claude-haiku-4-5` is
  likewise outdated; use `claude-haiku-5-5` for the cheap first test. Confirm
  against the Claude API model list at deploy time, since this goes stale fast.
- **`max_tokens` and stop reasons.** `max_tokens: int = 1024` (about L200) is
  low if extended thinking is ever enabled (thinking tokens count against it).
  Only `stop_reason == "refusal"` is handled; `"max_tokens"` is not, so a
  truncated answer would be sent to Telegram as if complete. Handle it
  explicitly (append a "cut off" marker or retry with a larger cap).
- **Missing `anthropic` on the Vercel worker.** Vercel installs
  `apps/cron_worker/requirements.txt` (`vercel.json` `installCommand`), and that
  file, like the root `requirements.txt`, does not list `anthropic`. With
  `LLM_ASSISTANT_ENABLED` and a key set, `complete()` raises `RuntimeError`
  (lazy import), and the broad `except Exception` in `handler._llm_reply`
  swallows it and returns `help_text()`. The result is a silently dead feature
  with only a warning in the logs. Add the dependency to the worker
  requirements (mind the bundle-size limit the notes discuss) *and* consider
  surfacing the failure instead of falling back to `/help`.
- **Context is empty while data is frozen.** `build_context` reads today's and
  yesterday's digests plus 7/14/30-day trends from `Storage`. With the Tandem
  sync broken and Supabase pump data stopping around 2026-08-23, those windows
  are empty today, so the model would answer from "no data" context. That
  changes once the sync fix lands; test the assistant after it, not before.
